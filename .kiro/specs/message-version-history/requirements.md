# 消息版本历史功能需求文档

## 1. 功能概述

为 AI 消息添加版本历史功能，允许用户在重新生成 AI 回复后，查看和切换不同版本的回复内容。

## 2. 用户故事

### 2.1 作为用户，我希望能够查看 AI 消息的历史版本

**验收标准：**

- 在有多个版本的 AI 消息下方显示版本切换器
- 版本切换器显示当前版本号和总版本数（例如：1/3）
- 版本切换器包含左右箭头按钮用于切换版本

### 2.2 作为用户，我希望重新生成时保留历史版本

**验收标准：**

- 点击"重新生成"按钮时，原有内容作为历史版本保存
- 新生成的内容作为最新版本显示
- 版本号自动递增
- 历史版本持久化存储到数据库

### 2.3 作为用户，我希望能够在不同版本之间切换

**验收标准：**

- 点击左箭头切换到上一个版本
- 点击右箭头切换到下一个版本
- 在第一个版本时，左箭头禁用
- 在最后一个版本时，右箭头禁用
- 切换版本时，消息内容实时更新

### 2.4 作为用户，我希望版本历史能够持久化

**验收标准：**

- 刷新页面后，版本历史仍然保留
- 切换会话后再回来，版本历史仍然保留
- 版本历史存储在数据库中

## 3. 功能需求

### 3.1 数据库设计

#### 方案 A：创建独立的版本表（推荐）

创建 `message_versions` 表存储消息的所有版本：

- `id`: 版本 ID（主键）
- `message_id`: 关联的消息 ID（外键）
- `version`: 版本号（从 1 开始）
- `content`: 版本内容
- `created_at`: 创建时间

`messages` 表添加字段：

- `current_version`: 当前显示的版本号（默认为最新版本）

#### 方案 B：在消息表中添加版本字段

在 `messages` 表中添加：

- `version`: 当前版本号
- `version_history`: JSON 格式存储历史版本

**选择方案 A**，因为：

- 更符合数据库规范化原则
- 便于查询和管理
- 支持更复杂的版本功能扩展

### 3.2 后端 API

#### 3.2.1 获取消息的所有版本

```
GET /api/messages/:id/versions
响应：
{
  success: true,
  data: [
    { version: 1, content: "...", created_at: "..." },
    { version: 2, content: "...", created_at: "..." },
    { version: 3, content: "...", created_at: "..." }
  ]
}
```

#### 3.2.2 切换消息版本

```
PUT /api/messages/:id/version
请求体：
{
  version: 2
}
响应：
{
  success: true,
  data: {
    id: 123,
    content: "...",
    current_version: 2
  }
}
```

#### 3.2.3 修改重新生成逻辑

- 重新生成时，将当前内容保存为历史版本
- 新内容作为最新版本
- 更新 `current_version` 为最新版本号

### 3.3 前端 UI

#### 3.3.1 版本切换器组件

位置：AI 消息底部，消息操作按钮上方

布局：

```
[消息内容]
[◀ 1/3 ▶]  [收藏] [复制] [重新生成]
[时间]
```

样式：

- 居中显示
- 左右箭头按钮
- 中间显示版本信息（当前版本/总版本数）
- 禁用状态的箭头显示为灰色

#### 3.3.2 版本切换交互

- 点击左箭头：切换到上一个版本
- 点击右箭头：切换到下一个版本
- 切换时显示加载状态
- 切换完成后更新消息内容

### 3.4 前端逻辑

#### 3.4.1 消息数据结构扩展

```typescript
interface Message {
	id: number
	conversation_id: number
	role: 'user' | 'assistant'
	content: string
	created_at: string
	is_favorited?: number
	current_version?: number // 当前版本号
	total_versions?: number // 总版本数
}
```

#### 3.4.2 版本管理

- 加载消息时，同时获取版本信息
- 缓存已加载的版本内容，避免重复请求
- 切换版本时，更新本地消息内容

#### 3.4.3 重新生成逻辑修改

- 调用重新生成 API 时，后端自动保存历史版本
- 前端接收新版本后，更新版本信息
- 显示最新版本内容

## 4. 非功能需求

### 4.1 性能要求

- 版本切换响应时间 < 500ms
- 支持至少 10 个版本的存储和切换

### 4.2 用户体验

- 版本切换动画流畅
- 禁用状态的按钮有明确的视觉反馈
- 版本信息显示清晰

### 4.3 数据一致性

- 版本号连续且唯一
- 删除消息时，同时删除所有版本
- 版本内容不能为空

## 5. 边界情况

### 5.1 只有一个版本

- 不显示版本切换器
- 或显示但左右箭头都禁用

### 5.2 版本切换失败

- 显示错误提示
- 保持当前版本不变

### 5.3 重新生成失败

- 不创建新版本
- 保持原有版本不变

## 6. 实现优先级

### P0（必须实现）

- 数据库版本表创建
- 重新生成时保存历史版本
- 版本切换 API
- 前端版本切换器 UI
- 版本切换功能

### P1（应该实现）

- 版本切换动画
- 版本信息缓存
- 错误处理和提示

### P2（可以实现）

- 版本对比功能
- 版本删除功能
- 版本导出功能

## 7. 技术约束

- 使用 SQLite 数据库
- 后端使用 Node.js + Express
- 前端使用 Vue 3 + TypeScript + Element Plus
- 遵循现有代码风格和架构
